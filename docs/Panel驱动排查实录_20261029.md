# Panel 驱动排查实录 — 2026-10-29

## 结论先行

**card0 出不来的根因不是驱动写得不对，是 dts 里 panel 节点被 disabled 了。**

```dts
// sm8550-meizu-21note73.dts 第 2001 行（修复前）
/* ==== panel disabled (m2381 面板与 m2468 不匹配) ==== */
&display_panel { status = "disabled"; };
```

这一行是 2026-10-28 调试 m2381 BOE 面板时留下的——那版 `CONFIG_DRM_PANEL_BOE_MEIZU20=y` 会让设备崩，所以把整个 panel 节点禁掉了。后来写 m2468 驱动时完全忘了它。

**后果链**：
```
panel@0 status=disabled
  → of_graph 不把该节点算进 graph
  → dsi_bind() 里 devm_drm_of_get_bridge(dev, of_node, 1, 0) 返回 -ENODEV
  → component bind 失败
  → component_master_add_with_match() 等不到全部组件
  → msm_drm_bind() 不执行
  → drm_dev_register() 不执行（msm_drv.c:177）
  → 没有 /dev/dri/card0
```

**证据**：修复前 `/proc/device-tree/soc@0/display-subsystem@ae00000/dsi@ae94000/panel@0/status` 读出 `disabled`，而父节点 `dsi@ae94000/status` 是 `okay`。

## 排查过程中踩的坑（按严重度）

### 坑 1：假 panel 驱动对 regulator 零保护 → 内核空指针崩溃

```c
// 子代理写的 panel-m2468-fake.c，probe 里：
ctx->vddio = devm_regulator_get_optional(dev, "vddio");
if (IS_ERR(ctx->vddio))
    ctx->vddio = NULL;              // 失败就置 NULL，不报错

// prepare 里：
ret = regulator_enable(ctx->vddio); // NULL 进去 = 空指针解引用 → oops
```

**症状**：刷入后设备完全失联（无 COM16、不进 mainline、不进 fastboot），只能手动长按进 fastboot。

**修复**：所有 `regulator_enable` 都包在 `if (ctx->vddio) { ... }` 里。

**教训**：`devm_regulator_get_optional` 返回 NULL 是完全合法的（表示没有这个 supply），调用方必须检查。`regulator_enable(NULL)` 不会返回错误，是直接崩。

---

### 坑 2：这个内核用的是新 DRM panel API

```
✅ devm_drm_panel_alloc(dev, type, member, funcs, connector_type)
✅ devm_drm_panel_add(dev, panel)
✅ drm_panel_of_backlight(panel)

❌ drm_panel_init()          —— 这个内核没有
❌ 手动 devm_kzalloc + drm_panel_init
```

**证据**：`include/drm/drm_panel.h` 里只有 `__devm_drm_panel_alloc` / `devm_drm_panel_alloc` 宏，没有 `drm_panel_init`。

**教训**：写驱动前先看目标内核的头文件，不要按老版本 API 写。

---

### 坑 3：`FB_BLANK_UNBLANK` 需要 `<linux/fb.h>`

```
#include <linux/backlight.h>    ← 只有这个不够
#include <linux/fb.h>           ← 还要这个
```

---

### 坑 4：`make olddefconfig` 会吃掉手动加的配置

**这次**：跑了 `olddefconfig` 后 CONFIG 行数从 4699 掉到 2789，所有关键项（DRM_MSM、ARM_SMMU、SM_GPUCC_8550、PHY_QCOM_QMP_UFS…）全部消失。

**恢复**：`cp .config.pre_panel .config`。

**教训**：
- 改配置**直接编辑 `.config`**（用 sed 精确改那一行），不要用 `scripts/config` + `olddefconfig`
- 每次改配置前先 `cp .config .config.bak_$(date +%H%M)`
- 检查配置时 **grep 模式必须带 `CONFIG_` 前缀**（我因为漏了这个前缀，误判了一次"所有配置都丢了"，虚惊一场）

---

### 坑 5：Mu 的 FVMAIN 只剩 1432 字节

```
FVMAIN [99%Full] 6356992 total, 6355560 used, 1432 free
```

**风险**：dtb 稍有变动就可能压不进去，Mu 编译显示 Success 但实际运行失败。

**对策**：每次改 dtb 后重编 Mu，要检查 FV 剩余空间；剩余 < 2KB 时要警惕。

## 驱动设计（最终版）

`drivers/gpu/drm/panel/panel-meizu-m2468.c`（440 行）

```c
// 两种模式，默认 FAKE，DT 可切
enum m2468_mode {
    M2468_MODE_FAKE = 0,   // 只注册 drm_panel，不发任何 DSI 命令（验 card0 用）
    M2468_MODE_REAL,       // 发送从原厂 dtbo 提取的 84 条初始化序列
};

// DT 属性切换
meizu,panel-mode = "real";   // 或 "fake"
```

**模式选择理由**：先 FAKE 验 card0（确认整条 DRM 链路通），再 REAL 验出图。每次只动一个变量。

### 初始化序列来源

`drivers/gpu/drm/panel/ili7838e_seq.h`（552 行，从原厂 Android dtbo 提取）

原厂 `qcom,mdss-dsi-on-command` 的 7 字节 wire format：
```
u8  dtype      0x05=short write / 0x15=short write+1param / 0x39=long write
u8  last       last command in set
u8  vc         virtual channel
u8  flags      ack/wait
u16 wait_ms    delay after (LE)
u8  dlen       payload length
u8  payload[]
```

5 档刷新率全部提取：`ili7838e_on_{120,144,90,60,30}hz`
- 120/144/90Hz 之间只差一条 `81 xx`（0x2d 页刷新率寄存器：00/01/03）
