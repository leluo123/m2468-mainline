## 二、根因链条（完整闭环）

```
ABL 按「即将跳 Android 内核」的方式交出 SPMI arbiter
        ↓
Mu 的 SPMIDxe 期望接手已配好的状态 → 报 "SPMI bus busy" ×4
        ↓
PmicDxe 拿不到有效句柄 → 同步异常 @0xC66DC8A0 → CpuDeadLoop
        ↓
PMIC 从未初始化 ⇒ 所有 LDO 不供电
        ↓
内核 probe 任何需要 PMIC 供电的外设（UFS / display / USB PHY / i2c SE）
        ↓
synchronous external abort 或硬件复位
```

**这是所有此前"看不明原因的重启"的唯一解释。**

| `0x0c42e60` cnfg+0xE60 | `0x00000000` | EE 配置全 0 |
| `0x0c42e64` cnfg+0xE64 | `0x00000000` | |
| `0x0c42e68` cnfg+0xE68 | `0x00000000` | |
| `0x0c42e6c` cnfg+0xE6C | `0x00000000` | |
| `0x0c42e70` cnfg+0xE70 | `0x00000000` | |

| `0x0c500004` ch0 CONFIG | `0x00000000` | |

**结论：所有关键寄存器都是 0 —— 说明 ABL 根本没配置 SPMI arbiter（不是配置错，是压根没配）。SPMIDxe 期望"已配好"，于是直接失败。**

**批量扫描时出现 `Bus error`**：因为内核的 `spmi-pmic-arb` 驱动已经 `ioremap` 了该区域，用户态 `/dev/mem` 再映射同一物理区会冲突。**⇒ 要读完整状态必须在内核驱动 probe 之前（即 Mu 阶段）。**

## 四、一并修正的三个 dts 配置错误（均已验证生效）

| 错误 | 现象 | 修正 | 结果 |
|---|---|---|---|
| **PM8010 不存在** | `regulators-6/7: ldo1: could not find RPMh address for resource index` ×3 | 删掉 `regulators-6`/`regulators-7`（它们是 nura m2381 专用，m2468 原厂 dts 里根本没有） | **报错彻底消失** |
| **freq-table-hz 长度错** | `ufshcd: freq-table-hz len mismatch` | 数清 `clock-names` = **8 个**（core_clk / bus_aggr_clk / iface_clk / core_clk_unipro / ref_clk / tx_lane0_sync / rx_lane0_sync / rx_lane1_sync），需 16 值 | 校验通过 |
| **OPP 与 freq-table 互斥** | `ufshcd_parse_operating_points: operating-points and freq-table-hz are incompatible` → `OPP parse failed -22` | 内核源码硬性判据（`ufshcd-pltfrm.c:430`）：两者同时存在直接 `-EINVAL`。我们已有 `ufs_opp_table`（opp-hz 8 值，正确） | 删 `freq-table-hz`，保留 OPP |

### UFS 最终仍崩的原因

```
ufshcd_populate_vreg: Unable to find vccq2-supply regulator, assuming enabled
```

`vccq2-supply` 缺失 → 内核只是"假装 enabled" → 第一次真正访问硬件即崩。

**但这只是表象**：UFS 的 VCC/VCCQ 都由 PMIC 供给，**PMIC 没初始化，任何配置都救不了它**。

## 五、这一轮踩的关键坑（都已解决，写进经验）

| 坑 | 现象 | 解法 |
|---|---|---|
| **BootShim 直写 SPMI 必崩** | 卡魅族 logo，Mu 一行日志都没有 | ABL 退出后 SPMI 区被 XPU 保护，BootShim 无权限。**必须改在 Mu 的 DXE 阶段** |
| **Mu 也用 FdtBlob** | 关掉整个 i2c hub → Mu 自己几秒重启 | 只关 SE，保留 hub 本体 |
| **DXE 顺序 ≠ Dispatch 顺序** | 驱动加了但不执行 | Depex 在 dispatch 中执行，由 Depex 决定 |
| **PmicDxe 崩溃会挡住后续一切** | 加了诊断驱动但屏幕上什么都没有 | 先关 PmicDxe；崩溃点之后的所有 DXE 都不会执行 |
| **Mu 的 ConOut 是串口** | `exec > /dev/tty0` 无效 | `USE_CUSTOM_DISPLAY_DRIVER=0` 时 console 只有串口；要用 `DEBUG()`（Qcom debug port → crash handler 上屏）或 kmsg |
| **`exec > /dev/kmsg` 放在挂载前** | init 输出全丢，屏幕空白 | 必须先 `mount -t devtmpfs none /dev`，`/dev/kmsg` 才存在 |
| **init 退出即 panic** | `Attempted to kill init!` | PID 1 绝不能退出，结尾用 `while true; do sleep 30; done` |
| **dts 里 `#` 注释无效** | `syntax error` | cpp 的 `#` 在 dts 里不是注释；要真删除 |
| **标签名 ≠ 节点名** | `&video_codec`/`&isp`/`&ufshc` 全不存在 | 真实标签：`iris` / `camss` / `gpu`；无标签的用路径 `&{/soc@0/usb@a600000}` |
| **dts 已有同名块导致 append 失效** | `if '&iris {' not in s` 判断跳过，静默不动 | 直接 append，dtc 取最后一条 |
| **dtb 不重编** | dts 改了 dtb 时间戳不变 | `rm -f dtb && touch dts && make` |
| **root 跑 Mu 编译失败** | `ModuleNotFoundError: coloredlogs` | Mu 必须普通用户；WSL 里一律用 `/mnt/c/...` |

## 六、下一步（唯一正确的方向）

**SPMI arbiter 需要被初始化，而它必须在「内核 ioremap 之前」完成 —— 也就是 Mu 的 DXE 阶段。**

`SpmiResetDxe` 已经写好并成功编进 Mu（`m2468Pkg/Drivers/SpmiResetDxe`），Depex 已从 GOP 改回 `TRUE`（最早执行，不会被后续崩溃挡住），输出走 `DEBUG()`。

**但它的输出还没在屏幕上看到** —— 需要确认 Mu 的 DebugPort 是否真的能上屏（Mu 自己的 `SPMI bus busy` 能上屏，说明通道存在）。

**下一步动作**：
1. 把 `SpmiResetDxe` 的 Depex 改成依赖 `gEfiCpuArchProtocolGuid`（比 TRUE 稍晚，确保 CpuDxe 已初始化，`DEBUG()` 才可用）
2. 刷一次，看 `[SPMI] core VERSION = 0x70000000` 是否出现
3. 出现后，在驱动里**写** EE 配置寄存器，让 APSS 拥有全部通道
4. 若 PMIC 起来（PmicDxe 不再崩）→ **UFS/display/USB 全部恢复，rootfs 可用**

**备选**：在 Mu 里跑 UEFI Shell，用 `mm` 命令交互读 SPMI（不依赖写驱动）。
