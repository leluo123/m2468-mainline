## 一、根因最终确认（100% 证据）

### 实测屏幕日志（`Mu-pmic-on` 版，PmicDxe 恢复后）

```
CPU Vectors region not present in cfg file !
SPMI bus busy
SPMI bus busy
SPMI bus busy
SPMI bus busy

Synchronous Exception at 0x00000000C66DC8A0
```

### 与 `移植记录_20261027.md` 的预言**逐字吻合**

> SPMIDxe 初始化 → **SPMI bus busy ×3** → 失败
> → PmicDxe 拿空句柄 → **同步异常 @ 0xC66DC8A0** → CpuDeadLoop

**连崩溃地址 `0xC66DC8A0` 都完全一致。**

### 因果链（至此完全闭合）

```
ABL 按「即将跳 Android 内核」的方式初始化 SPMI arbiter
        ↓
Mu 的 SPMIDxe 期望接手「干净」状态 → 报 SPMI bus busy ×4
        ↓
PmicDxe 拿不到有效句柄 → 同步异常 @0xC66DC8A0 → CpuDeadLoop
        ↓
PMIC 从未初始化 ⇒ 所有 LDO 不供电
        ↓
内核 probe 任何外设（I2C SE / UFS / USB PHY…）读寄存器
        ↓
synchronous external abort（总线从设备无应答）
```

**⇒ 之前所有 `geni_i2c_probe` 崩溃、`qcom_smd_edac` 崩溃、所有 dts 改动、6.14 vs 7.3 之争，全部是在给这个根因打补丁。**

## 三、已确认的关键技术事实（可复用）

### 3.1 启动链（实测）

```
ABL → BootShim(gzip 压缩 FD) → Mu-UEFI(SEC/PEI/DXE/BDS)
    → ESP/EFI/BOOT/BOOTAA64.EFI (= Linux EFI zboot, zstd 压缩的 44MB Image)
    → 内核
```
- ESP = `rawdump` 分区（sda22，256MB FAT32，label `MUESP`），7z 可读写
- Mu 镜像 = Android boot image v4（kernel 字段 = gzip 压缩的 FD）

### 3.2 DT 供给

- `DtPlatformDxe` 通过 `GetSectionFromAnyFv(&gDtPlatformDefaultDtbFileGuid /* 25462CDA-221F-47DF-AC1D-259CFAA4E326 */, EFI_SECTION_RAW, ...)` 取 FdtBlob
- **Mu 自己也用这份 DT** ⇒ 不能随意 disable 节点（关掉整个 i2c hub → Mu 崩）
- `Hardware name:` 是 DMI 字符串（`PcdSmbiosSystemManufacturer/Model/BoardModel`），**与 DT 无关**；判断 DT 要看 `Machine model:`

### 3.3 原厂 m2468 的真实拓扑（源码级）

`github.com/meizu-sm8550-kernel/android_kernel_meizu_sm8550-devicetrees` @ `lineage-24.0`
- `meizu/m2468-kalama.dts` 672KB + 5 个 overlay（本机是 index 4 = MP）
- **QUP 只有 7 条通道在用**：
  | SE | 类型 | 挂什么 |
  |---|---|---|
  | 0xa80000 | I2C | NFC + tms_thn31 |
  | 0xa90000 | **SPI** | 触摸 goodix-berlin |
  | 0x888000 | **SPI** | UWB sr100 |
  | 0x89c000 | I2C | pm8008i + aw2016 |
  | **0x988000** | I2C | fsa4480@42（**hub 下唯一启用的 SE**） |
  | 0x898000 / 0xa9c000 | UART | 蓝牙 / console |
- hub 下 10 个 SE 中 **9 个 disabled**，nura 的 m2381 dts 启用了 3 个（988000/98c000/994000）→ 后两个在 m2468 上不存在

### 3.4 SPMI

- arbiter base = `0xc42d000`（从原厂 dts）
- `SPMIDxe.efi`（49KB）里 "SPMI bus busy" 字符串 @ `0x68ce`，错误码映射：`0x1` → bus busy，`0x8` → 另一个
- 内核 `spmi-pmic-arb.c` **不做 arbiter 初始化**（假设 bootloader 已配好）
- `abl.img` 是 ELF32 容器，`unwrap-qcom-pil.py` 可解出 1MB FV + **610,504 B 的 LinuxLoader PE**（PE 头 @ 0xb8）

## 四、唯一的修复路径（移植记录「路 A」）

**在 `BootShim.S` 的 `br x5` 之前，重置 SPMI arbiter。**

`BootShim.S` 只有 59 行，插桩点很干净：

```asm
_Entry:
  br    x5      ← 在这里之前插入 SPMI 复位序列
```

**需要的东西**：SPMI arbiter 的 EE/通道重置寄存器序列。

**获取方法（下一步工作）**：
1. 反汇编 `LinuxLoader.efi`（610KB，119,147 行），找 SPMI arbiter 初始化；
   特征：对 `base+0x0E00` 区域的写、`VERSION`(0x0) 读、`MAPPING_TABLE`(0xB00+4n) 写
2. 或从 `SPMIDxe.efi` 的失败点反推「它期望什么状态」
3. 或参考其他 Qualcomm 平台的 SPMI arbiter reset 序列（`spmi_pmic_arb_probe` 的 vendor 分支）

**估算工作量**：1–2 天（反汇编 + 上机验证 3–5 轮）

## 五、旁路方案（不修 SPMI 也能跑）

**目标**：让内核不依赖 PMIC 供电就能启动到 initramfs。

1. **禁用所有需要 PMIC LDO 的外设**：i2c hub、UFS 之外的存储、USB PHY、显示
   —— 但 UFS 也需要电（虽然 ABL 已上电，可能撑得过）
2. **只留 UART / 内存 / CPU**，先验证「内核能跑到 initramfs」
3. 能跑到 initramfs 后，至少能拿到完整 dmesg（initramfs 里可以写盘）

**价值**：把「看不到日志」这个死结解开，之后所有调试都容易。
