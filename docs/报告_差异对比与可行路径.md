## 0. 结论摘要（先看这五条）

1. **`m2468Pkg/FdtBlob/Source.txt` 里那张「从 2026-09 到 10 月每一轮」的台账，不是 m2468 的台账，是 m2381 的台账被机械改名。** 证据：对 `m2468Pkg/FdtBlob/Source.txt` 做 `m2468→m2381 / 21note→20 / "MEIZU 21 Note"→"Meizu 20"` 替换后，与 `m2381Pkg/FdtBlob/Source.txt` **逐字节相同**（`diff` 无输出）。台账里 iris / nfc / AW8697 触感 / panel 时序 / va-dai-link / r68 INTB / r69 ramoops 全部是**在 Meizu 20 上**做的设备日实测。
2. **`m2468Pkg/FdtBlob/sm8550-meizu-21note.dtb` 与 `m2381Pkg/FdtBlob/sm8550-meizu-20.dtb` 是同一份 DTB 家族**：我们从 GitHub 拉下来的「nura 原版 m2381 dtb」`sha256=c061acd9…`，与 `m2381Pkg/FdtBlob/sm8550-meizu-20.dtb` **哈希完全一致**（都是 137,380 B）。我们改 3 行 model/compatible 得到的 `m2468.dtb`（137,392 B）只多了 12 字节字符串。
3. 所以我们刷进去的东西，**本质就是一台 Meizu 20 的设备树**（硬件描述层面），只是字符串改成了 21 Note。**方法论没有在 m2468 上跑过，一次也没有。**
4. **崩溃点已精确到指令与源码行**：`geni_i2c_probe+0x390` = `ldr w3,[x3]`，`x3 = se->base + 0x68` = `GENI_FW_REVISION_RO`；`addr2line` 回溯 = `__raw_readl (arch/arm64/include/asm/io.h:80) ← readl_relaxed ← geni_se_read_proto (include/linux/soc/qcom/geni-se.h:328)`。即**该 SE 寄存器块的第一次 MMIO 读**就外部中止；而它前面的 `clk_prepare_enable(core)`、`geni_se_resources_on()`（s-ahb + se 时钟 + pinctrl）**全部返回 0（成功）**。
5. **我方内核是 6.14.11，nura 是 7.3.0**（已从 `raw.githubusercontent.com/.../meizu20-t4b/Makefile` 实测：`VERSION=7 / PATCHLEVEL=3 / SUBLEVEL=0`）。两者 geni-i2c 的 probe 流程**结构性不同**：7.3 在任何寄存器访问前先 `pm_runtime_resume_and_get()` → `geni_se_resources_activate()`；6.14 是裸 `clk+icc+pinctrl` 后直接读寄存器，**全程不投票设备自身的 power-domain**。DT 是 7.3 上验过的，6.14 上就多了一层「上电没保证」的风险。

> 一句话：**不是「同样的方法论在我们这里失败」，而是「我们拿到的是一台 Meizu 20 的成品，把它改名后当真机 m2468 的移植成果来用」。**

## 3. `geni_i2c_probe+0x390` SError 根因分析

### 3.1 精确到指令与源码行（**硬证据**）

```
$ aarch64-linux-gnu-nm -n vmlinux | grep -w geni_i2c_probe
ffff800080deb3ec t geni_i2c_probe          # 函数 0x6b4 字节，与 panic 里 "/0x6b4" 吻合
# +0x390 → 0xffff800080deb77c
```

```
ffff800080deb764:  mov  x0, x19
ffff800080deb768:  bl   geni_se_resources_on          ← 返回 0（否则跳 +0x504 错误路径）
ffff800080deb76c:  mov  w3, w0
ffff800080deb770:  cbnz w0, ...+0x504
ffff800080deb774:  ldr  x0, [x19]                     ← x0 = se->base
ffff800080deb778:  add  x3, x0, #0x68                 ← 0x68 = GENI_FW_REVISION_RO
ffff800080deb77c:  ldr  w3, [x3]        ★ PANIC 在这里（+0x390）
```

```
$ aarch64-linux-gnu-addr2line -e vmlinux -f -i 0xffff800080deb77c
__raw_readl          ./arch/arm64/include/asm/io.h:80
readl_relaxed        ./include/asm-generic/io.h:336
geni_se_read_proto   （geni-se.h:328 → drivers/i2c/busses/i2c-qcom-geni.c:881 内联）
```

**结论（无争议）**：
- 崩溃是 **该 SE 寄存器块的第 1 次 MMIO 读**，读的是 `GENI_FW_REVISION_RO (0x68)`，用于判断该 SE 的协议号是否 = I2C。
- 崩溃前，内核已经：`devm_platform_ioremap_resource` 成功、`devm_clk_get("se")` 成功、`clk_prepare_enable(core_clk)` 成功（+0x378 `bl clk_enable`）、`geni_icc_get` + `geni_icc_set_bw` 成功、`geni_se_resources_on()` 成功（内部依次 `clk_bulk_prepare_enable(wrapper→s-ahb)`、`clk_prepare_enable(se)`、`pinctrl_pm_select_default_state`）。
- 也就是说：**时钟框架层面「全部已开」，硬件层面「这条地址没人应答」**。这是典型的 (a) 该 SE 所在电源域/QUP 本体未真正上电，或 (b) `reg` 指向了不存在的地址。

### 3.2 这次崩溃发生在哪个设备上（含证据强度声明）

- **日志里的 unit address 不可信**：`9c800000` 在 nura 的 dts/dtsi、我方的 dts/dtsi、原厂 `merged_full.dts`、`live.dts` 里**全都不存在**（前一晚的 `dump_qup.sh` 全树扫描 `reg==0x9c800000` 结果为空）。同一段日志里 `i2c@9880000`（多一个 0）、`typec-retimer@lc`（`1c`→`lc`）也明显是抄写/OCR 噪声 → **这段日志是从屏幕照片转写的，不能作为地址证据**。
- **可以用的是**：紧邻崩溃前那条 `Fixed dependency cycle(s) with /soc@0/geniqup@9c0000/i2c@…/typec-retimer@…` —— 它唯一对应 **`geniqup@9c0000` 下的 I2C master-hub SE + 其上的 `onnn,nb7vpq904m` typec-retimer**。
  - 而 `typec-retimer@1c` **只存在于 nura 的 m2381 DTS**（`sm8550-meizu-20.dts:1475`），我方 DTS 完全没有这个节点（`grep retimer` 只命中 pmic_glink endpoint）。
  - **这条报警本身就是「当前跑的是一份 m2381 形状的 DT」的直接物证。**
- 「`Bus frequency not specified, default to 100kHz`」这条也吻合：nura DT 里 `i2c@988000` 写了 `clock-frequency=400000`（`0x61a80`），不会打这句。实测 nura 的 137,380 B dtb 中，**只有 `i2c@98c000`(hub_3) 没有 `clock-frequency`**（其余 888000/988000/994000/a80000/a90000 全是 `0x61a80`）；而我方 DT 里 `i2c_hub_2@988000` 也没写（`sm8550-meizu-21note.dts:609` 只有 `status="okay"`）。→ 两种 DT 各有唯一候选：**nura 形状 ⇒ 98c000；我方形状 ⇒ 988000**。
- **诚实结论**：崩溃设备 =「`geniqup@9c0000`（I2C master hub）下、`status=okay` 且未写 `clock-frequency` 的那个 SE」。配合上一条的 retimer 环报警（retimer 在 988000 上），**倾向 988000**；但 nura 形状下 988000 是有 400 kHz 的，出现这句又与「retimer 在 988000」矛盾 → **两条日志线索互相冲突，现有材料无法唯一确定，必须按 §4-P0 修好 pstore 再复现取原始日志**。

### 3.3 「DT 里缺什么会 SError」——按可能性排序

| # | 机制 | 是否成立 | 判别方法 |
|---|---|---|---|
| **A** | **DT 是 7.3 的、内核是 6.14.11**：7.3 的 `geni_i2c_probe` 走 `resources_init()` → `devm_pm_runtime_enable()` → `geni_i2c_init()` → **`pm_runtime_resume_and_get()`** → `power_on = geni_se_resources_activate()` → 才 `geni_se_read_proto()`；6.14.11 是 inline `clk+icc+pinctrl` → **直接读寄存器**，全程**不 resume 设备**（`pm_runtime_enable` 在 probe 末尾 929 行才调）。SE 节点带 `power-domains = <&rpmhpd RPMHPD_CX>` + `required-opps`，而 `cx` 在 6.14 的 `rpmhpd.c` 里**没有 `always_on`**。→ 6.14 下这块 SE 的 genpd 从未被 vote，硬件是否上电完全取决于 bootloader 遗留状态。 | **高度可疑（已有代码级证据）** | 同 DT 下给 `&i2c_master_hub_0` 加 `status="disabled"`（一次干掉 10 个 hub SE）再启动：过了 42 s 就锁定此因 |
| **B** | **板级硬件描述错机**：m2381 的 DT 在这条总线上挂了 m2468 不存在的 retimer/pm8008i（见 §2.4），fw_devlink 因这条错误的 port-graph 产生环 → `Fixed dependency cycle` → 链接被删 → **probe 顺序不再受供应商约束**，SE 可能先于其供电/时钟供应商就位而被访问 | 可疑（环是实锤，顺序是推断） | 把 `i2c@988000`/`98c000` 的子节点整段删掉（只留空总线）再启动 |
| **C** | **reg 指到空洞**：若真如日志 `9c800000`，则 ioremap 的地址在本 SoC 无译码 → 首次访问必 SError。 | 与所有 DT 数据矛盾（无此节点），**判定为抄写噪声**，但不能 100% 排除（因为日志来源不可靠） | 修好 pstore 后看原始 `geni_i2c <addr>.i2c` |
| **D** | **RPMh/AOP 交接态坏**（我们 10-27 已论证：ABL→Mu 的 SPMI arbiter 状态与 mainline 假设不符；`spmi-pmic-arb.c` 从不初始化 arbiter）→ 所有 `rpmhpd`/regulator vote 静默失效 → 需要新上电的块永远没电 | 可疑（与 `vreg_ldo9` 死等、`SPMI bus busy` 同源） | 用 `pd_ignore_unused` + 关闭所有 i2c hub 做对照；或在 `spmi_pmic_arb_probe()` 补 arbiter 复位 |
| **E** | Mu 侧 `FdtBlob` 的 DT 与 ESP 上的 DT 不一致（双源）：Mu 会把 FdtBlob 作为 UEFI 配置表交给内核，但若 ESP 的 `BOOTAA64.EFI`（zboot）自带 dtb 或 cmdline 里写死 `devicetree`，实际生效的可能不是我们换的那份 | 无法从现有材料排除 | 启动后打印 `/sys/firmware/fdt` 的 size + sha 与 FdtBlob 比对（**这条必须做，否则整轮实验都可能无效**） |

### 3.4 顺带查实的一个「必须改」：ramoops 地址

台账 r69 明确记：**m2381 上 ramoops 必须从 `0xa5100000` 搬到 `0xa8000000`，因为 Mu 的 Display Demura 区 `0xA2A80000 + 0x2B00000` 每次 boot 覆写**。
我方 dts 至今仍是：

```dts
mz_ramoops: ramoops@a5100000 {        /* sm8550-meizu-21note.dts:989 */
    reg = <0x0 0xa5100000 0x0 0x200000>;
```

这**正好解释**了我们 10-27 记录的「ramoops 配好了但重启进 Android 后 `/sys/fs/pstore/` 是空的」。**没有 pstore = 没有原始日志 = 只能靠屏幕照片 = 才有 `9c800000` 这种噪声。** 这是所有后续诊断的前置条件。

## 4. 我们能不能、怎样才能搓出正确的 m2468 设备树？

**能。但不是「改一改 nura 的 dts」能到的事**——nura 自己为了 m2381 一台机，台账上就是 9 轮、每轮设备日实测。m2468 是另一台机，等价工作量至少同量级。按可行性排序：

### 路径 P1（首选，1–2 天）：把内核换成 nura 的 7.3.0 树，先拿到「能启动」的确定基线

- **做什么**：`git clone https://github.com/RiverKawa271828/linux-mobile-ports -b meizu20-t4b`；用它们的 `sm8550-meizu-20.dts` **原样**（不改 model/compatible）编 dtb；内核配置沿用它们的（pmaports `linux-meizu-meizu20` 的 config），Mu 侧 FdtBlob 放这份 dtb。
- **为什么可行度最高**：DT 与内核是**同一棵树上的一对**，7.3 的 geni/i2c 有 `pm_runtime + resources_activate`（§3.3-A 的缺口不存在），这是唯一被证明「在这块 SoC 上跑起来过」的组合。我们现在的 6.14.11 + 7.3 的 DT 属于**跨版本拼装**。
- **所需数据**：网络可达 GitHub（本机 WSL 当前**不通**，需 Windows 侧代理；`curl` 在 WSL 里直接失败）；`~15 GB` 磁盘；`aarch64-linux-gnu-` 工具链（已有）。
- **工具**：`make ARCH=arm64 O=build defconfig` + 其 config 片段；`dtc`（已有）。
- **验证判据**：① 串口/`earlycon=efifb` 出现 `geni_i2c` probe 不再 SError；② 到 `initramfs` 的 `/ #`；③ `/sys/firmware/fdt` 的 sha == FdtBlob 里的 dtb sha（同时验证 §3.3-E）。
- **预计耗时**：拉树+编译 3–5 h（首次），刷机验证 30 min/轮。
- **风险**：仍会用 m2381 的板级描述 → 触摸/面板/NFC/充电大概率不对，但**能启动**是分水岭。

### 路径 P2（次选，可与 P1 并行，半天/轮）：在 6.14.11 上做「最小可信 DT 阶梯」，先证明崩溃属于哪一类

- **做什么**（严格单变量，照 nura 的台账格式记录）：
  1. **P0-a**：ramoops 改 `0xa8000000`（§3.4）→ 刷一次，确认 `pstore` 能拿到日志。**没有这步，后面全是瞎猜。**
  2. **P0-b**：确认生效的 DT 就是 FdtBlob 里那份（比对 `/sys/firmware/fdt` 的 size/sha）。
  3. **S1**：`&i2c_master_hub_0 { status="disabled"; }`（一次性禁掉 10 个 hub SE）→ 若不再 SError ⇒ 锁定 §3.3-A/B。
  4. **S2**：只保留 `i2c@994000`（触感）+ `i2c@988000` 但**删掉 retimer/pm8008i 子节点**（m2468 上没有）→ 看是否仍崩。
  5. **S3**：把 `&qupv3_id_0`(a80000/a90000 那组)、`&i2c0`、`&i2c4` 逐个打开，每次只加一个。
- **所需数据**：现有 dts + §2.4 的原厂总线对照表；原厂 DT 已在手（`merged_full.dtb`）。
- **验证判据**：每轮的 `dmesg`（pstore）+ 是否越过 42 s + 是否到 initramfs。
- **预计耗时**：每轮 20–30 min（编译 8 min + 刷机 + 抓 log）；S1–S3 共约 2–3 h。
- **价值**：即便最后换 7.3，这套阶梯也能告诉我们**哪几个节点是 m2468 真正需要的**。

### 路径 P3（终局，2–4 周，等价于 nura 的工作量）：从原厂 DT 反推一份真正的 m2468 板级 DT

- **做什么**：以 `/home/shrp/m2468/merged_full.dtb`（860,880 B，已含 base + 5 个 dtbo 片段）为唯一事实源，逐子系统「翻译」成 mainline 绑定：
  - 电源：`apps_rsc` 全量 vreg（原厂 58+ 条 rail 的电压/负载约束）→ 直接决定能不能 probe；
  - 总线：按 §2.4 表逐条重建 `i2c@89c000 / 988000 / 98c000 / 994000 / a80000` 的子节点（pm8008i/j、cs35l43、fsa4480、aw8697、tms,nfc）；
  - 显示：panel compatible + `qcom,panel-phy-timings`（用台账 v3b 口径，别用被否决的 byte-scale）；
  - 触感：`awinic,aw8697` + reset ACTIVE_LOW；
  - 录音：`va-dai-link` + PDM dmic；
  - 存储/USB/PCIe：UFS 的 `vcc/vccq` 轨、`dr_mode`、`mode-switch`。
- **所需数据/工具**：原厂 DT（有）、`dtc`/`fdtget`（有）、一台能稳定出日志的通道（pstore 或 USB CDC-ACM gadget）、**以及「单变量 + 设备日」的纪律**（这是 nura 台账真正值钱的部分）。
- **验证判据**：按优先级分档 —— ① 到 initramfs；② 触摸可用；③ 面板点亮；④ 触感/充电/录音；每档都要有 `dmesg` 证据。
- **预计耗时**：2–4 周（nura 光触感就花了 3 轮 + 1 次判决）。

**不建议的路径**：继续「拿 nura 的 dtb 改 model/compatible」。已证伪——改完 12 字节，崩得一模一样，因为它和原来那份是同源同构。
