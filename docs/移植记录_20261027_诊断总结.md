## 二、已经打通的技术链

```
ABL → boot_b(Mu-UEFI, SPMIDxe on) → UEFI → ESP/BOOTAA64.EFI
                                              ↓
                                    zboot 自解压 PE（12MB, MZ+zimg）
                                              ↓
                                    内核接管，earlycon=efifb 输出
```

关键突破点：**`earlycon=efifb`** —— 之前一直「零输出」的真因是输出通道选错：
- `earlycon`（无参数）→ 走 DTB 的 stdout-path → serial0（UART 物理引脚，没接线）= 全丢
- `console=tty0` → 要等 efifb 驱动注册（在 setup_arch 之后）
- **`earlycon=efifb`** → 直接用 UEFI 的线性 framebuffer，setup_arch 最早期就能输出 ✅

## 四、当前卡点（明天从这里开始）

### 现象
```
所有 initcall 跑完（52.9 秒，clk_disable_unused 是最后一个）
    ↓
之后不动 / 或有大量重复 initcall 输出
    ↓
init 永远不执行（屏幕无 "INIT STARTED"）
```

### 根因（今天最后发现的）
**对比 nura 的 dts（2046 行 / 56 个节点覆盖） vs 我们的（1079 行 / 38 个节点）**

我们**完全缺失**的关键节点：

```
&ufs_mem_hc                ← UFS 控制器配置
&tlmm                      ← pinctrl（GPIO 引脚配置）★最关键
&apps_rsc                  ← RPMh 资源配置
&pm8550_gpios              ← PMIC GPIO
&pmk8550_gpios
&pmk8550_rtc               ← RTC
&pon_pwrkey / &pon_resin   ← 电源键
&pm8550b_eusb2_repeater    ← USB PHY repeater
&mdss / &mdss_dsi0 / &mdss_dsi0_phy  ← 显示
&gpu
&i2c0 / &i2c4 / &i2c10     ← I2C（触摸屏等）
&remoteproc_adsp/cdsp/mpss
&sleep_clk                 ← sleep clock 频率
&qupv3_id_0 / &qupv3_id_1
&swr1 / &swr2
&uart7 / &uart14
&camss / &ipa / &iris / &crypto / &pcie0...
```

**因果链**：
```
没配 &tlmm（pinctrl）→ 所有外设引脚处于复位默认态
        ↓
时钟/电源/总线全部不可用
        ↓
UFS、I2C、PMIC 设备 probe 全部 -EPROBE_DEFER
        ↓
deferred probe 无限重试
        ↓
do_initcalls 永不结束 → init 永不执行
```

### 已试过但无效的参数（不要再试）
- `deferred_probe_timeout=8` / `initcall_deferred_probe_timeout=8` —— 只在 `initcalls_done` 之后才计时，而 initcalls 本身就卡住，形成死锁
- `nosmp` —— 能让内核跑更久（52→211 秒），但陷入 defer 循环，仍到不了 init
- `clk_ignore_unused` / `pd_ignore_unused` —— 无效
- `pstore_blk`（blkdev=259:59, best_effort=1）—— **时序死结**：`late_initcall` 执行时 UFS 还在 defer，`early_lookup_bdev` 必然失败；pstore_blk 不支持重试
- `panic_on_warn` + `panic=-1` —— WARN 能变 panic，但 WDT 没接管时仍会被硬件复位（`sm8550.dtsi` 原本没有 watchdog 节点，已手动补 `watchdog@17c10000` 但未验证驱动是否 probe 成功）

### 已排除的误判
- ❌ 「`Found dependency cycles!` 是根因」→ 实际是 `Fixed dependency cycle(s)`，fw_devlink 的正常提示，环已被修复
- ❌ 「SPMI arbiter 完全不可访问」→ 实际能读到 VERSION（v7）和 buffer config，只是事务被拒
- ❌ 「`SPMI: Init hw_ver` / `Init buf config` 是内核打的」→ 是 **Mu 的 SPMIDxe** 打的，内核里没有这些字符串
