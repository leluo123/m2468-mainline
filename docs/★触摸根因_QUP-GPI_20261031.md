# ★触摸根因_QUP-GPI_20261031.md

> 魅族 21 Note (m2468, SM8550) · Armbian 26.8.1 + Linux 7.3.0
> 2026-10-31 深夜 至 11-01 凌晨

---

## 一句话结论

**Mu-Silicium 的 DT 里 `spi@a90000` 少了 `dmas` 属性。**

**这不是芯片问题、不是 TrustZone 锁死、不是 CS 极性、不是硬件故障。
是一行 DT 遗漏，它引发了后面九轮的全部假象。**

---

## 完整因果链

```
Mu DT: spi@a90000 { ... }  没有 dmas / dma-names
        ↓
spi_geni_grab_gpi_chan()
  → dma_request_chan(dev, "tx") 失败
  → 返回 -EPROBE_DEFER 或 -ENODEV
        ↓
spi-geni-qcom.c:682  switch(fifo_disable) case 1:
  → 拿不到 GPI channel，fallthrough 到 FIFO 模式
        ↓
但 GENI_IF_DISABLE_RO (0xa90064) bit0 = 1
  → 这块 SE 设计上就不走 FIFO
  → FIFO 事务发出去没有硬件响应
        ↓
spi 事务超时 → -110 (ETIMEDOUT)
        ↓
goodix_berlin probe → regmap_raw_read 读回全 0 → memcmp 失败
  → "device confirm failed, rx_buf: 00 00 00 00 00 00 00 00"
  → probe failed with error -22
```

## 铁证：同一颗 QUP 下 6 个兄弟节点全都写了 dmas

`geniqup@ac0000` 下挂 SE0..SE6：

| 节点 | dmas |
|---|---|
| spi@a80000 (SE0) | `<0x79 0x00 0x00 0x01  0x79 0x01 0x00 0x01>` ✅ |
| spi@a84000 (SE1) | `<0x79 0x00 0x01 0x01  0x79 0x01 0x01 0x01>` ✅ |
| spi@a88000 (SE2) | `<0x79 0x00 0x02 0x01  0x79 0x01 0x02 0x01>` ✅ |
| spi@a8c000 (SE3) | `<0x79 0x00 0x03 0x01  0x79 0x01 0x03 0x01>` ✅ |
| **spi@a90000 (SE4)** | **（空白）** ❌ ← 触摸用的这个 |
| spi@a94000 (SE5) | `<0x79 0x00 0x05 0x01  0x79 0x01 0x05 0x01>` ✅ |
| spi@a98000 (SE6) | `<0x79 0x00 0x06 0x01  0x79 0x01 0x06 0x01>` ✅ |

**格式：`<GPI_phandle 方向(0=tx/1=rx) SE编号 分组(1)>`**
**GPI phandle `0x79` = `dma-controller@a00000`（geniqup@ac0000 所属的那颗）**

**SE 编号从 0 到 6 连号，只有 SE4 漏了。**

## 第二个坑：`CONFIG_QCOM_GPI_DMA=m` 但整树 0 个 .ko

```
$ grep CONFIG_QCOM_GPI_DMA .config
CONFIG_QCOM_GPI_DMA=m

$ find . -name "*.ko" | wc -l
0
```

**只有 `.o`（172KB），没有 `.ko`。说明编译只跑到编译阶段，没走 modpost 链接。
驱动永远不会被加载 → 就算 DT 写了 dmas 也拿不到 channel。**

**修复：**
```bash
cd /home/shrp/lmp73
export ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu-
make -j$(nproc) modules        # 12 分钟，生成 Module.symvers + 1328 个 .ko
# 结果：Module.symvers 1,374,305 B，gpi.ko 197,320 B (md5 309c6ce8)
```

**注意：`make M=drivers/dma/qcom modules` 单独编会失败
（modpost 报所有符号 undefined，因为缺 Module.symvers）。必须先跑整树 `make modules`。**

## 我走过的弯路（全部记录，避免重犯）

| 轮次 | 我以为是 | 实际 |
|---|---|---|
| P1 | 删 dmas 走 FIFO | 能 probe 但事务超时，因为 FIFO 硬件被禁 |
| P2 | ldo9 供电不足 | 供电正常 |
| P3 | 去 cpha/cpol | 无影响 |
| E29 | goodix 模块未加载 | 改内建，仍 -110 |
| E30 | 清 `SE_DMA_IF_EN` (0x2008) 强行开 FIFO | instant crash，0x2008 不是可运行期改的 |
| R-1 | 走 spi-gpio 绕开 GENI | 事务成功但 IC 不答（因为没有真正的 SPI 时序质量） |
| **误判** | **"MISO 被外部拉低 = 硬件故障"** | **错。当时 spi-gpio 驱动还占着引脚，我和它抢同一组 GPIO，读数是我自己造的假象** |
| **误判** | **"QTS/TrustZone 锁死，无解"** | **半错。QTS 确实给 SE4 加载 SPI 固件（proto=1），但那只是"用 SPI"，不等于"不通"** |
| R6 | 改成 I2C 绕开 | `geni_i2c a90000: Invalid proto 1`，proto=1 是 SPI，改不了（FW_REVISION_RO 只读） |
| FORCE_DEFAULT | 写 0x20 bit0 复位 SE | 系统立即死亡，硬件复位才恢复。**不能裸写，必须按 QUP 时序** |

## 关键寄存器实测值（GENI SE4 @ 0xa90000）

```
0x10  GENERAL_CFG         = 0x00000048
0x20  FORCE_DEFAULT_REG   = 0x00000000   （写 1 会打死系统）
0x24  OUTPUT_CTRL         = 0x0000007f
0x40  SE_GENI_STATUS      = 0x00000000
0x48  SER_M_CLK_CFG       = 0x00000011
0x4c  SER_S_CLK_CFG       = 0x00000000
0x60  CLK_CTRL_RO         = 0x00000001   M_CLK/S_CLK 都没开
0x64  IF_DISABLE_RO       = 0x00000001   ★ FIFO 禁用（设计如此，走 DMA 的 SE）
0x68  FW_REVISION_RO      = 0x00000102   proto=1 (SPI), fw 0.2  ★ 只读
0x74  FW_MULTILOCK_MSA_RO = 0x00000000
```

**枚举值（include/linux/soc/qcom/geni-se.h:34-40）：**

**`Invalid proto 1` 的真实含义 = SE 里的固件是 SPI 的。**

## 我做的修复

### ① DT 补 dmas（md5 `af04f630`）

```dts
spi@a90000 {
    compatible = "qcom,geni-spi";
    interrupts = <0x00 0x165 0x04 0x00>;
    dmas = <0x79 0x00 0x04 0x01 0x79 0x01 0x04 0x01>;   ← 新增
    dma-names = "tx", "rx";                              ← 新增
    status = "okay";                                     ← disabled → okay
    touchscreen@0 { compatible="goodix,gt9916"; status="okay"; };
};
spi-gpio { status = "disabled"; };   ← 保持关闭（spi-gpio 路线已证伪）
```

Mu R7 = `★待刷_Mu_R7_spidma.img` md5 `0bcf5426e542b10d15895bcbe8cf7679`

### ② 编出 gpi.ko

```
gpi.ko  197,320 B  md5 309c6ce8203556211e27ec9913950bef
```

### ③ initramfs 内置 insmod（ESP md5 `e693a9cc`）

**为什么放 initramfs 而不是启动后手动 insmod：**
`spi` 是 built-in，第 24 秒就 probe 了（那时 gpi 还没加载）。
但 insmod gpi 会触发 kernel 的 `driver_deferred_probe_trigger()`，
spi 会重试并拿到 channel。放 initramfs 里能保证在 switch_root 前完成，
避免 systemd 阶段还要人工干预。

```sh
# init 第 11-23 行
echo "[gpi] loading..." > /dev/tty0
insmod /gpi.ko 2>/dev/null && echo "[gpi] loaded OK" > /dev/tty0 \
    || echo "[gpi] insmod FAILED" > /dev/tty0
sleep 1
echo 1 > /sys/bus/platform/drivers_probe 2>/dev/null
sleep 1
GPIDBG=$(dmesg | grep -c "geni_spi.*Failed to get tx DMA ch" 2>/dev/null)
echo "[gpi] spi dma-fail count=$GPIDBG" > /dev/tty0
```

**initramfs.cpio.gz: 1,012,888 → 1,067,119 B（+54KB）**

## 附带发现：启动慢 5 分钟的真正原因

```
[  24.388411] gcc-sm8550 100000.clock-controller: sync_state() pending due to a90000.spi
[  24.388404] qcom-rpmhpd 17a00000.rsc:power-controller: sync_state() pending due to a90000.spi
[  24.388405] qnoc-sm8550 interconnect-1: sync_state() pending due to a90000.spi
[  24.388406] qnoc-sm8550 16e0000.interconnect: sync_state() pending due to a90000.spi
[  24.388407] qnoc-sm8550 1600000.interconnect: sync_state() pending due to a90000.spi
[  24.388408] qnoc-sm8550 24100000.interconnect: sync_state() pending due to a90000.spi
[  24.388409] qnoc-sm8550 interconnect-0: sync_state() pending due to a90000.spi
[  24.388411] gcc-sm8550 100000.clock-controller: sync_state() pending due to a90000.spi
[ 228.663082]   a90000.spi  geni_spi: Failed to get tx DMA ch   ← 足足等了 204 秒！
[ 327.368442] platform a90000.spi: deferred probe pending: geni_spi: Failed to get tx DMA ch
```

**`spi` 卡在 deferred probe，而 gcc / interconnect / rpmhpd 全都在 `sync_state()` 等它。
每个依赖方串行等待超时，叠加起来就是 5 分钟。**

**所以：修好 spi 的 DMA = 触摸通 + 启动快 4 分钟以上。一个根因，两个解。**

`systemd-analyze blame` 的真实耗时（651ms 用户会话等）都是假象，
因为 systemd 计时器是从它自己启动开始算的，前面的 228 秒它根本没在跑。

## 如果 GPI 还是不通

**上游 `drivers/dma/qcom/gpi.c` 的 `of_match` 表里没有 `qcom,sm8550-gpi-dma`，
靠 DT 里第二个 compatible `"qcom,sm6350-gpi-dma"` 兜底（ee_offset = 0x10000）。
如果 sm8550 的 EE 布局和 sm6350 不同，probe 会失败或崩。**

**那就需要给 gpi.c 加 sm8550 条目，或者验证 ee_offset 是否正确：**
```c
ee_offset = (uintptr_t)device_get_match_data(gpi_dev->dev);
gpi_dev->ee_base = gpi_dev->ee_base - ee_offset;
// dma-controller@a00000, reg=0xa00000, ee_offset=0x10000
// → ee_base = 0x9F0000
```
