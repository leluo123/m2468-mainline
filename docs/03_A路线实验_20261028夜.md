# A 路线实验报告 —— BootShim 直写 SPMI：结果与教训

**实验时间**：2026-10-28 21:20–21:53
**结果**：❌ 失败（设备卡死在魅族 logo）
**但**：拿到了完整的技术地图，明确了 A 路线的正确实施层

---

## 一、这次做了什么

给 `BootShim.S` 插入了 SPMI arbiter 复位序列，在 `br x5`（跳进 Mu）之前执行：

```asm
_Entry:
  movz  x9,  #0x4000
  movk  x9,  #0x0c40, lsl #16        /* 0x0c400000 core  */
  movz  x10, #0x0000
  movk  x10, #0x0c50, lsl #16        /* 0x0c500000 chnls */
  movz  x11, #0xd000
  movk  x11, #0x0c42, lsl #16        /* 0x0c42d000 cnfg  */

  mov   w12, wzr
  str   w12, [x10, #0x0000]          /* 清 ch0 CMD */
  str   w12, [x10, #0x1000]          /* 清 ch1 CMD */
  str   w12, [x10, #0x2000]          /* 清 ch2 CMD */
  str   w12, [x10, #0x3000]          /* 清 ch3 CMD */

  ldr   w13, [x9]                    /* 读 VERSION */
  br    x5
```

同时恢复了 PmicDxe（作为判据：它崩不崩 = SPMI 好没好）。

## 二、结果

**设备卡死在魅族 logo**，连 Mu 的第一行日志都没出来。

**⇒ BootShim 在 `br x5` 之前就异常了，Mu 根本没启动。**

## 三、为什么失败（两个可能，按可能性排序）

### 可能 1：XPU 保护（最可能）

ABL 在退出前会把 SPMI / PMIC 相关寄存器区域锁进 XPU（eXtended Protection Unit）白名单，只允许特定 master 访问。

**BootShim 跑在 ABL 退出后的环境，master ID 可能不在白名单里** → 访问 `0x0c400000` / `0x0c500000` 触发 XPU violation → 同步异常 → 死机。

**支持证据**：BootShim 的拷贝循环访问 `FD_BASE`（另一块内存）是正常的，说明 MMU 正常；差的只是**访问权限**。

### 可能 2：MMU 未映射

ABL 退出时可能把 MMU 改成只映射部分区域（DRAM + 少量 IO），`0x0c400000` 不在其中。

但 BootShim 能正常拷贝到 `FD_BASE`（DRAM），所以 MMU 至少是开着的；如果 SPMI 区域没映射，同样会 abort。

**两种可能都指向同一个结论：BootShim 不是操作 SPMI 的正确层级。**

## 四、这次拿到的重要技术地图（都是确定的事实）

### SPMI arbiter 的 5 个寄存器块（dts 原文）

```
core   = 0x0c400000  0x3000       VERSION @ +0x0000
chnls  = 0x0c500000  0x400000     通道寄存器
obsrvr = 0x0c440000  0x80000
intr   = 0x0c4c0000  0x20000
cnfg   = 0x0c42d000  0x4000   ★  EE 配置区
```

**`0xc42d000` 就在 XBL 二进制里出现过一次**（文件偏移 `0x5e2aa`），确认这是 cnfg 基址。

**SPMIDxe 读的 `0xe60/0xe64/0xe68/0xe6c/0xe70`** = `cnfg + 0xE60` 起的 5 个 32 位寄存器（间隔 4 字节 = 5 个 EE）。

### 通道寄存器布局（Linux 内核 `spmi-pmic-arb.c`）

```
每个通道 0x1000 字节：
  +0x00  CMD
  +0x04  CONFIG
  +0x08  STATUS
  +0x10  WDATA0
  +0x14  WDATA1
  +0x18  RDATA0
  +0x1C  RDATA1
```

### 内核不做 arbiter 初始化

`spmi-pmic-arb.c` 里只有 `pmic_arb_base_write()`（通道级），**没有任何 EE 配置 / reset 代码**——Linux 假设 bootloader 已经配好。

### XBL 里确实有 SPMI 代码

xbl_a.img（3.5MB，ELF32 容器）字符串表：
```
0e9808  Driver Init # SPMI Transn: %d
0eef5b  SPMI_TX: 1 byte SPMI_RD %dus
0ef4fe  SpmiBus
5e2aa   ★ 0xC42D000（cnfg 基址常量）
```

**但 ABL（LinuxLoader，610KB PE）里一条 SPMI 字符串都没有** → SPMI 初始化在 XBL，不在 ABL。

## 五、A 路线的正确做法（下次从这里开始）

**不要在 BootShim 里直接碰寄存器**，改在 **Mu 的 DXE 阶段**做。理由：

1. Mu 的 DXE 跑在自己的 MMU 环境，页表齐全
2. Mu 的 SPMIDxe 本身就成功访问过 SPMI（它能报 "bus busy"，说明读到了 STATUS）
3. **⇒ 在 SPMIDxe 加载之前插一个小 DXE**，用 Mu 的 IoLib 做寄存器访问，安全且可控

**实现方式**（三选一）：

**方案 A1（最简单）**：改 Mu 的 `APRIORI.inc` 顺序，在 SPMIDxe 之前加一个自定义 DXE（用 EDK2 写几十行），读 cnfg+0xE60..0xE70 并打印到串口/屏幕，然后按需写。

**方案 A2**：写一个 Mu Shell 脚本（`.nsh`），用 `mm` 命令直接读写：
```
mm 0x0c42d000, 0x00000000
```
但 Shell 启动在 SPMIDxe 之后，可能太晚。

**方案 A3**：把 BootShim 的做法搬到 Mu 的 PEI 阶段（PEI 有临时 MMU，但同样可能被 XPU 拦）。

**推荐 A1**，因为只有它能拿到"SPMIDxe 之前"的完整环境，且有打印能力（这是现在最缺的）。
