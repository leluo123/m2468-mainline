## 一、最重要的三个发现（按重要性）

### 🔴 发现 1：我们改的 Mu FdtBlob 很可能从来没生效过

**证据链**：

1. 启动链（`移植记录_20261027.md` §完整启动链）：
   ```
   ABL → BootShim(gzip) → Mu-UEFI(BDS) → BOOTAA64.EFI → 内核
   ```
2. `BOOTAA64.EFI` 的真实身份（本次实测，前 32 字节）：
   ```
   4d 5a ... 7a 69 6d 67 ("zimg") ... 7a 73 74 64 ("zstd")
   → 这是 Linux 内核的 EFI zboot 镜像（CONFIG_EFI_ZBOOT=y），不是 GRUB，也不是 Mu
   ```
3. 内核 cmdline 实测（`.config:565`）：
   ```
   CONFIG_CMDLINE="acpi=off earlycon=efifb keep_bootcon console=tty0 fbcon=font:TER16x32
                    nomodeset nokaslr numa=off nosmp clk_ignore_unused pd_ignore_unused
                    nowatchdog watchdog_thresh=0 loglevel=7 deferred_probe_timeout=8
                    panic=-1 rdinit=/init"
   CONFIG_CMDLINE_FORCE=y
   ```
   → **`acpi=off` 早就在里面了**，所以「ACPI 抢了 DT」这条假设可以彻底排除。
4. rawdump 分区（sda22，本次已 dd 出来，256MB FAT32）实际内容：
   ```
   EFI/BOOT/BOOTAA64.EFI   13,103,616   (zboot 内核)
   initramfs.cpio.gz        1,006,305
   dtb                        113,810   ← 是我们 25KB 手写 dts 编的那份
   ```
   **没有 /Image、没有 grub.cfg**（GRUB 是早期方案，已废弃）。
5. EFI zboot 不吃 ESP 里的 `/dtb` 文件——它只认 **UEFI 提供的 FDT**（即 Mu 的 FdtBlob）或 appended dtb。

**⇒ 结论：DT 唯一来源 = Mu 的 `FdtBlob/sm8550-meizu-21note.dtb`。**
**但崩溃日志的 `Hardware name: Meizu MEIZU 21 Note(meizu20, BIOS 3.9 10/27/2026)` 是 DMI 字符串，说明 Mu 的 `DtPlatformDxe` 会用 SMBIOS 改写 DT 的 `/model`——所以 model 不能用来判断 DT 是否生效。**

### 🔴 发现 2：我们手里的 dtb 本质是 Meizu 20 的，从没在 m2468 上验证过

子 Agent 实证（`报告_差异对比与可行路径.md` §0）：

| 事实 | 证据 |
|---|---|
| `m2468Pkg/FdtBlob/Source.txt` 那张「逐轮台账」是 **m2381 台账机械改名** | 做 `m2468→m2381 / 21note→20` 替换后与 m2381Pkg 的 `Source.txt` **逐字节相同** |
| `m2468Pkg/.../sm8550-meizu-21note.dtb` 与 `m2381Pkg/.../sm8550-meizu-20.dtb` 是同一份 | 都是 137,380 B，sha256 `c061acd9…` 一致 |
| 我们改 3 行 model/compatible 得到的 m2468.dtb | 137,392 B，只多 12 字节字符串 |

**⇒ 这一夜的 dts 改动全部是在「一台 Meizu 20 的设备树」上做字符串替换，硬件描述层面从来没针对 m2468 做过一次真实验证。**

### 🔴 发现 3：内核版本代差（6.14 vs 7.3）是 SError 的结构性原因

子 Agent 实测（`报告_geni_i2c崩溃根因.md` §1.2 + 本次验证）：

| | 我方 6.14.11 | nura 7.3.0 |
|---|---|---|
| 寄存器访问前 | 裸 `clk_prepare_enable` + `geni_se_resources_on`（只开 clk/pinctrl） | `pm_runtime_resume_and_get()` → `geni_se_resources_activate()` |
| power-domain 投票 | **完全没有** | 有（runtime PM） |
| `.power_on` 回调 | 无 | `geni_se_resources_activate` |

**崩溃点精确到指令**（`报告_geni_i2c崩溃根因.md` §1.2）：

```
ffff800080deb760: cbnz w0, ...             ; clk_prepare_enable 返回检查
ffff800080deb768: bl   geni_se_resources_on  ; 开 wrapper s-ahb + se clk + pinctrl
ffff800080deb76c: mov  w3, w0
ffff800080deb770: cbnz w0, ...             ; 返回 0（成功）
ffff800080deb774: ldr  x0, [x19]           ; x0 = se.base
ffff800080deb778: add  x3, x0, #0x68       ; base + GENI_FW_REVISION_RO
ffff800080deb77c: ldr  w3, [x3]            ; ← 崩溃 PC（+0x390）：第一次 MMIO 读
```

**⇒ 这是 probe 流程里第一次真正碰硬件，前面所有步骤都返回成功。SError = 总线从设备无应答 = 地址不对 或 时钟/电源没开。**

另有一条隐藏坑（`drivers/soc/qcom/qcom-geni-se.c`）：
```c
static int geni_se_clks_on(struct geni_se *se)
{
    struct geni_wrapper *wrapper = se->wrapper;
    if (!wrapper) return 0;   ← wrapper 为 NULL 时静默跳过，不开 s-ahb 时钟！
    ...
}
```

## 二、哨兵 C 实验结果（2026-10-28 09:20 实测）—— 决定性

**刷入 `Mu-sentinel-c.img`（只关 `i2c_hub_2` = `0x988000`）后的崩溃日志：**

```
[39.993734] geni_i2c 98c000.i2c: Bus frequency not specified, default to 100kHz
[40.086867] Internal error: synchronous external abort: 0000000096000010 [#1] PREEMPT SMP
[40.363616] CPU: 0 UID: 0 PID: 12 Comm: kworker/u32:0 Tainted: G W 6.14.11 #52
[40.823353] pc : geni_i2c_probe+0x390/0x6b4
[40.915278] lr : geni_i2c_probe+0x300/0x6b4
```

### 两个结论

**① DT 确实生效了**

关掉 `0x988000` 后，崩溃**转移到了 `0x98c000`**（下一个启用的 hub SE）。这是最干净的单变量证据——**我们改的 FdtBlob 一直在起作用**。

（同时纠正我此前的读图错误：之前几次读到的 `9c8000` / `9c800000` 都是照片模糊导致的误读，真实崩溃地址一直是 hub 下某个实际启用的 SE 地址。）

**② 根因在 hub 层，不在某个 SE**

| 实验 | 崩溃地址 |
|---|---|
| hub_2(0x988000) 启用 | `0x988000` 相关 |
| **hub_2 关掉** | **`0x98c000`（下一个启用的 SE）** |

**关一个就崩下一个 ⇒ 每个启用的 hub SE 都会崩 ⇒ 问题在它们共用的东西上：wrapper 的 `s-ahb` 时钟 / CX power-domain。**

这正好对上版本差异：

```c
7.3:  pm_runtime_resume_and_get()  →  geni_se_resources_activate()   ← 会投票 power-domain
6.14: 裸 clk + icc + pinctrl      →  直接读 SE+0x68                  ← 没人投票
```

**⇒ 6.14 内核 + 7.3 的 DT，SE 的电源域无人投票打开，首次读寄存器必 SError。改 dts 解决不了，必须换内核。**

### 结论：B 路径（换 7.3）是唯一正确的解

已在执行：7.3.0 树（`/home/shrp/lmp73`，1.8 GB）+ 从 6.14 迁移的 .config，正在编译 `Image`。

### 🔬 子 Agent 补充的关键事实（本次夜间并行调研）

**① 崩溃机制彻底闭环**

原厂 reserved-memory 里的保护区（`no-map`，CPU 读取即外部中止）：
```
cvp_region@9c200000  : <0x9c200000  0x700000>    → 0x9c200000 ~ 0x9c900000
cdsp_region@9c900000 : <0x9c900000  0x2000000>   → 0x9c900000 ~ 0x9e900000
```

而 `0x9C8000` 落在 **QUP 窗口之外**（hub SE 仅 `0x980000`~`0x9a4000`，wrapper 到 `0x9C2000` 为止）。
**⇒ 软件认为已上电、硬件根本没有这个从设备 ⇒ 首读必 SError。机制确定，没有第三种可能。**

**② 原厂 m2468 只有 7 条 QUP 通道在用**（共 26 个 SE）

| SE 地址 | 类型 | 挂什么 |
|---|---|---|
| `0xa80000` | I2C | NFC `nq@27`(qcom,sn-nci) + `tms_thn31@28` |
| `0xa90000` | **SPI** | 触摸 `goodix-berlin@0`（reset gpio24 / irq gpio25） |
| `0x888000` | **SPI** | UWB `sr100@0`（ri gpio70 / ce gpio170 / irq gpio176） |
| `0x89c000` | I2C | `pm8008i@8/@9` + `aw2016@64` |
| **`0x988000`** | I2C (hub_2) | **子节点全是 disabled 桩** |
| `0x898000` | UART | 蓝牙 |
| `0xa9c000` | UART | console |

**③ 决定性差异**：nura 的 m2381 DTS 在 `0x988000` 上挂了 `nb7vpq904m` retimer（`typec-retimer@1c`），**而原厂 m2468 这个 SE 上什么都没有**。这正是「拿 m2381 的设备树跑 m2468」的物证。

**④ nura 的 DTS 血统**：骨架抄自第三方公开树 `silime/linux` 分支 `7.3.0-dev` 的 `sm8550-meizu-20-inf.dts`（魅族 20 Infinity 参考 DTS），不是 dtbo 整文件反编译。他的工作方法是「**三源 corpus + 白名单式重建**」：每个节点必须来自 vendor_boot base DTB / dtbo entry overlay / ABL 后 runtime FDT 三者之一，证不出来的降级为注释桩。

**⑤ 这套方法论可以平移到 m2468**（四件套与机型弱相关），但 corpus 必须重做，且有两条禁令：
- `remoteproc memory-region` 不能抄 base（他抄了 0x6080000，一轮就死）
- 原厂 GPIO flags 不能跨驱动照抄（极性语义相反）

## 五、真正的修复路径（按优先级，供你决策）

### 路径 1 ⭐ 推荐：把内核升到 7.3，和 nura 完全对齐

**理由**：nura 的 DT 是按 7.3 的 runtime PM 模型写的；6.14 缺 `pm_runtime_resume_and_get`，SE 的 power-domain 没人投票，天然会崩。

**做法**：
1. 拉 `RiverKawa271828/linux-mobile-ports`（分支 `meizu20-t4b`，7.3.0）——**现在网络已通（codeload 直连 14MB/s，实测 116MB/8s）**
2. 用他的 `sm8550-meizu-20.dts` + 完整 dtsi 编译
3. 按 m2468 改装（改 model/compatible + 按原厂事实修正 i2c 设备）
4. 编 `vmlinuz.efi`（zboot）→ 替换 ESP 的 `BOOTAA64.EFI`
5. 刷 rawdump

**风险**：7.3 的 .config 与 6.14 差异大，可能需要多轮配置调整。预计 2-4 小时。

### 路径 2：给 6.14 打 backport 补丁（改动最小）

把 7.3 的 runtime PM 逻辑搬进 6.14 的 `drivers/i2c/busses/i2c-qcom-geni.c` + `drivers/soc/qcom/qcom-geni-se.c`：

```c
// probe 里，在 clk_prepare_enable 之前插入
ret = devm_pm_runtime_enable(dev);
...
pm_runtime_set_active(dev);
ret = pm_runtime_resume_and_get(dev);   // ← 关键：投票 power-domain
```

**风险**：`geni_se_resources_activate` 是 6.15+ 的新 API，backport 需要连 `geni-se.h` 一起改。预计 1-2 小时 + 编译排错。

### 路径 3 ⭐ 最有价值：用原厂 m2468 设备树重建

**今晚的重大收获**——找到了真正的原厂设备树仓库：

```
https://github.com/meizu-sm8550-kernel/android_kernel_meizu_sm8550-devicetrees
分支：lineage-24.0
├── meizu/m2468-kalama.dts          672,711 B  ← m2468 完整 DT（反编译合并版）
├── meizu/m2468-overlay-00..04.dts  各 ~710 KB  ← 5 个 overlay
└── qcom/                           1024 个 Android dtsi
```

**这是「他们怎么搓出来的」的最终答案**：nura 台账里那些「原厂反编译/实测」的值，源头就是这类仓库。

**已用它验证的事实**（可直接采信）：
```
原厂 m2468:
  qcom,qupv3_i2c_geni_se@9c0000 { reg = <0x9c0000 0x2000>; ranges; }
    i2c@988000 { reg = <0x988000 0x4000>; status = "ok";
                 fsa4480@42 { compatible = "qcom,fsa4480-i2c"; reg = <0x42>; }
                 nq@64 { compatible = "rtc6226"; status = "disable"; } }
    i2c@980000/984000/990000/998000/99c000 → status = "disabled"

nura m2381 (我们手上的):
    i2c@988000 → typec-retimer@1c { compatible = "onnn,nb7vpq904m"; }
    i2c@98c000 → pm8008j@8,  i2c@994000 → haptics@5a
```

**⇒ 型号差异铁证**：m2468 在 0x988000 上挂的是 **fsa4480**，m2381 挂的是 **nb7vpq904m retimer**。我们一直用的 dtb 里是后者——**这颗芯片在 m2468 上根本不存在**。

**做法**：以原厂 `m2468-kalama.dts` 为事实源，逐节点对齐 mainline dts（regulator、pinctrl、i2c 从设备、panel、clock）。这是 nura 做过的事，工作量最大但最正。
