## 完整启动链（已全部打通）

### 1. ABL 加载 Mu

- `boot_b` 刷 Mu 的 `Mu-m2468.img`（Android boot.img 格式）
- ABL 按 boot.img 解析，把 FD 加载到 `0xA7100000`（大小 0x300000）
- BootShim.S 解压 FD 到 DDR，跳转到 Mu 入口

**关键**：Mu 镜像必须能被 ABL 接受（这是最难的关，作者 silime 花了 3 周）

### 2. Mu-UEFI 阶段

| 阶段 | 状态 | 说明 |
|---|---|---|
| SEC | ✅ | BootShim 搬运 + 跳转 |
| PEI | ✅ | 早期内存初始化 |
| DXE | ✅ | 各驱动加载（**SPMIDxe/PmicDxe 已摘除**） |
| BDS | ✅ | 启动管理器，能枚举 UFS 分区 |
| UI | ✅ | 能显示 logo、电池图标 |

**CPU Vectors warning**（`region not present in cfg file`）—— 无害，魅族 20 也报

### 3. GRUB 引导（本次新增）

**关键设计**：不依赖键盘，完全自动

```
分区：rawdump (sda22, 256MB, GPT 第 22 分区)
格式：FAT32 (mkfs.vfat -F 32)
内容：
  /EFI/BOOT/BOOTAA64.EFI   GRUB 2.06 (grub-mkimage, prefix=/EFI/BOOT)
  /EFI/BOOT/grub.cfg       自动执行，timeout=0
  /Image                   mainline kernel
  /dtb                     sm8550-meizu-21note.dtb
  /initramfs.cpio.gz       busybox arm64 + USB serial gadget
```

**为什么用 rawdump**：设备上没有空闲空间（userdata 占满 464GB），rawdump 是崩溃转储分区，256MB，格式化不影响 Android 启动。

### 4. mainline kernel 启动

**grub.cfg 关键参数**：
```
linux /Image console=tty0 console=ttyMSM0,115200n8 \
      earlycon=msm_geni_serial,0xa8c000,115200n8 \
      keep_bootcon rdinit=/init loglevel=8 ignore_loglevel
devicetree /dtb
initrd /initramfs.cpio.gz
boot
```

## 🔍 根因分析

**核心症状**：
```
[ 0.272411] qcom-rpmh-regulator 17a00000.rsc:regulators-6: ldo1: could not find RPMh address for resource ldo1
[ 0.272511] qcom-rpmh-regulator 17a00000.rsc:regulators-2: ldo1: could not find RPMh address for resource ldo1
```

**因果链**：
```
RPMh regulator 地址映射不全（dts 缺 vreg 定义）
        ↓
部分 regulator / power domain 拿不到
        ↓
GPU (adreno) 的 clock/power 依赖不满足
        ↓
3d00000.iommu 死等 12 秒才超时放弃
        ↓
4d00000.iommu 等依赖一直 -517
        ↓
后续驱动（UFS、显示、USB PHY）全部 EPROBE_DEFER
        ↓
内核卡在 deferred probe 循环，到不了 initramfs
```

**`could not find RPMh address for resource ldo1`** 是唯一的根因。

## ⚠️ 踩过的坑（重要）

### 1. SPMIDxe / PmicDxe 会崩

```
SPMIDxe 初始化 → SPMI bus busy ×3 → 失败
  → PmicDxe 拿空句柄 → 同步异常 @ 0xC66DC8A0 → CpuDeadLoop
```

**临时解决**：从 `APRIORI.inc` 和 `DXE.inc` 里注释掉这两个 INF。

**代价**：PMIC 不初始化（电量读不到、部分外设无电），但 **UFS 仍能工作**（ABL 已上电）。

### 2. dtb 修改无效（SPMI 相关）

SPMIDxe 在 **APRIORI**（强制早期），`DtPlatformDxe` 在 FDF 里（晚加载）→ **SPMIDxe 运行时 DTB 还没准备好**。

所以改 dts 的 spmi 节点（加 cnfg 区域、改节点名）**对 Mu 无效**，但对 Linux 内核仍然必要（已修，别撤）。

### 3. DEBUG 宏被编译掉

Mu 编译参数有 `-D MDEPKG_NDEBUG`，所有 `DEBUG((...))` 语句在编译期被消除。

**必须用** `gst->ConOut->OutputString()` 才能输出诊断信息。

### 4. GRUB 模块名 vs 命令名

| 模块名 | 命令名 |
|---|---|
| `fdt` | `devicetree` |

写 `--modules="devicetree"` 会报错（模块不存在）。
写 `fdt /dtb` 也会报错（命令不存在）。
**正确**：模块用 `fdt`，cfg 里用 `devicetree`。

### 5. GRUB 停在 `grub>` 命令行

原因：
- 没有键盘 → `menuentry` 的 timeout 不倒计时
- **解决**：cfg 里不用 `menuentry`，直接写命令序列（`linux` / `devicetree` / `initrd` / `boot`）
- GRUB 用 `grub-mkimage -p /EFI/BOOT` 固定 prefix，从分区读外部 cfg

### 6. 显示驱动全是模块 → 屏幕无输出

```
CONFIG_DRM=m
CONFIG_DRM_MSM=m                          ← 被 QCOM_OCMEM=m / QCOM_LLCC=m 卡住
CONFIG_DRM_PANEL_VISIONOX_VTDR6130=m      ← 被 BACKLIGHT_CLASS_DEVICE=m 卡住
CONFIG_BACKLIGHT_CLASS_DEVICE=m
```

**修复**（已验证可编译通过）：
```bash
./scripts/config -d QCOM_OCMEM -d QCOM_LLCC \
  -e DRM_MSM -e DRM_MSM_DPU -e DRM_MSM_DSI -e DRM_MSM_MDSS \
  -e BACKLIGHT_CLASS_DEVICE -e BACKLIGHT_PWM \
  -e DRM_PANEL_VISIONOX_VTDR6130
```

**⚠️ 注意**：全内置后如果 panel probe 失败，**会黑屏**（比没驱动更糟，earlycon 也被清了）。
建议：**调试阶段保持 `DRM_MSM=m`，用 keep_bootcon 看 earlycon**。

### 7. pstore 读不到日志

ramoops 配在 `0xa5100000`（与 vendor 一致），但重启进 Android 后 `/sys/fs/pstore/` 是空的 —— Android 内核接管同一区域时重置了。

### 8. USB serial gadget 没起来

initramfs 里配了 configfs + acm.usb0，但电脑上没出现新 COM 口。
**原因**：内核没跑到 initramfs（卡在 iommu），gadget 根本没执行。

## 🎯 下一步（17:40 更新，最重要的一条）

### 屏幕日志问题已解决 ✅

**`nomodeset` 是关键**：Mu 会通过 UEFI 传递 framebuffer 给内核，内核用 `simple-framebuffer` 在早期显示。但一旦真正的 DRM 驱动接管，如果 DRM 是模块（没加载），屏幕就断了。

加上 `nomodeset` 后，`simple-framebuffer` 会一直保留，**日志全程可见**。

**最终可用的 grub.cfg 内核参数**：
```
linux /Image console=tty0 earlycon keep_bootcon nomodeset rdinit=/init loglevel=8 ignore_loglevel
```

### 真实卡点：`vreg_ldo9` 设置电压后死等

日志最后三行：
```
[ 6.614657] qcom_scm: firmware: qcom_scm: untested machine, skipping
[ 6.614761] vreg_ldo9: Setting 3280000-3280000uV
[ 6.614883] vreg_ldo9: Setting 3280000-3280000uV
```

**注意**：
- `3280000` 这个值在我们的 dts 里**完全不存在**（我们的 `vreg_l9b_2p9` 是 2960000-3008000）→ 说明这是驱动运行时算的，或者是另一个 PMIC 的 LDO9
- 同一行**打印了 2 次** → 典型的 deferred probe 重试

**因果推断（关键）**：

```
RPMh regulator 设置电压
        ↓
RPMh 硬件把请求发给 AOP
        ↓
AOP 通过 SPMI 总线控制 PMIC
        ↓
★ SPMI 总线状态不对（ABL 用完没释放）
        ↓
AOP 拿不到 PMIC 应答
        ↓
regulator_set_voltage 同步死等 ← 卡在这里
```

**所以 SPMI 问题是贯穿 Mu 和 Linux 的同一条根因**：

| 场景 | 表现 |
|---|---|
| Mu 的 SPMIDxe 初始化 | `SPMI bus busy` ×3 → 失败 → PmicDxe 空指针崩溃 |
| Linux 的 rpmh-regulator | 设置电压死等（AOP 走 SPMI 拿不到 PMIC 应答） |

**结论：必须在 SPMI 层面解决，而不是在 Mu 或内核里绕。**

### 明天两条路（按性价比排序）

**路 A：在 BootShim 里释放 SPMI arbiter（推荐）**

- 位置：`BootShim.S`，在 `br x5` 跳 Mu 之前
- 需要：SPMI arbiter 的 EE 配置寄存器地址（`cnfg` 基址 0xc42d000 + 偏移）
- 线索：SPMIDxe 反汇编里读的是 `0xe60` / `0xe64` / `0xe68` / `0xe6c` / `0xe70` 这几个偏移（相对某个基址）
- 验证：Mu 启动时不再报 `SPMI bus busy`

**路 B：让 Linux 侧先重置 SPMI**

- mainline 的 `spmi-pmic-arb.c` probe 时不会重置 arbiter（假设硬件干净）
- 可以在 `spmi_pmic_arb_probe()` 里加一段写 cnfg 寄存器的复位序列
- 缺点：要改内核，且如果 AOP 侧状态是坏的，内核改也未必有用

**路 C（备选）：让 Mu 完全不碰 SPMI，同时确认 ABL 是否真的释放了**

- 已做：摘掉 SPMIDxe/PmicDxe
- 待验证：ABL 跳到 kernel 时 SPMI 到底是什么状态（Android 能正常工作说明 ABL→Linux 这条路是通的！）
- **重要线索**：Android 内核用同样的 SPMI 硬件能正常工作 → **说明 ABL→Linux 的 SPMI 交接是 OK 的**
- **那为什么 Mu/Linux(mainline) 不行？** 可能是 Mu 在中途碰过 SPMI（哪怕摘了驱动，PEI 也可能初始化），把状态搞坏了

**⭐ 路 C 的推论很关键**：如果 ABL→Linux 直接启动是通的，那问题就出在 **Mu 这个中间层**。可以试试**完全不让 Mu 碰 SPMI**（检查 PEI 里有没有 SPMI 初始化代码）。

### 🔑 17:47 最终定位（已确证）

**已验证的事实：**

1. **Mu 里只有 DXE 形式的 SPMIDxe/PmicDxe，PEI 完全不碰 SPMI**
   - `find Binaries/mars -iname '*pmic*' -o -iname '*spmi*'` → 全部是 DXE
   - 所以 `SPMI bus busy` 是 **ABL 留下的硬件状态**，不是 Mu 弄坏的

2. **mainline 的 `spmi-pmic-arb.c` 从不初始化 arbiter**
   - `grep -n writel drivers/spmi/spmi-pmic-arb.c` 只有 6 处，全是「发 SPMI 命令」和「清中断」
   - **没有任何 EE 配置 / 通道复位 / arbiter 初始化代码**
   - 它假设 bootloader 已经把 arbiter 配好了

3. **Android 的 vendor 驱动会做初始化**，所以 Android 能正常工作

**结论：**

```
ABL 按「即将跳 Android 内核」的方式初始化 SPMI arbiter
        ↓
Mu(UEFI) 启动，它的 SPMIDxe 期望的是「自己从头初始化」的干净状态
        ↓
状态不匹配 → SPMI bus busy → PmicDxe 崩溃
        ↓
（摘掉两个驱动后）Linux 接手
        ↓
mainline 的 spmi-pmic-arb 同样假设「干净状态」，不做初始化
        ↓
rpmh-regulator 通过 AOP→SPMI 控制 PMIC 时死等
```

**这不是 Bug，是「交接协议不匹配」—— Mu 和 mainline Linux 都假设自己是从 bootloader 接手干净硬件，但 ABL 交出来的是「已经为 Android 准备好」的状态。**

1. **Mu 能跑到 BDS 是巨大突破** —— 说明 ABL→UEFI 这条链在非官方机型上通了
