# v35 内核疑云 — 结案报告

**日期**：2026-10-29 · **范围**：只读分析（未改任何文件、未刷机、未碰设备）
**一句话结论**：`10,977,792` 那个 BOOTAA64.EFI **不是**刷进机器并且跑通的 v35 —— 它是 `/home/shrp/esp_v35.img`（10-28 21:09，#37）里的**砍配置退化版**。真正验证可用的 v35 是 `实验镜像_20261028/esp-v35-gpucc.img` 里的 **14,733,824 字节 / #54**。所以「10.9MB 却能跑」这个矛盾不存在：能跑的那个根本不是 10.9MB。**大小差异与 panel2 启动失败无关。**

## 3. 为什么是 10.9MB？纯粹是被砍的配置

- 退化版解压后内核 30.4MB，完整版 47.8MB，差 17.5MB；zstd-22 压完正好差 ~3.76MB（14.73 − 10.98）。比例自洽，不是截断、不是压缩参数、不是 initramfs 差异（三个镜像的 `initramfs.cpio.gz` md5 全同 `667cf168…`，1,006,305 字节）。
- 另注：`#54`(47,841,280) → `#58`(47,972,352) 配置清单相同却涨了 131,072 字节（正好 32 页对齐），说明**内核体积不是配置行的单调函数**（内嵌 dtb/对齐都会跳变），拿字节数当"配置是否完整"的判据本来就不可靠。

## 4. 大小差异与 panel2 失败的关系：排除

真实增量 v35(可用) → panel2 = 14868992 − 14733824 = **135,168 字节**，来源仅两处：
1. 新编进一个 panel 驱动（`CONFIG_DRM_PANEL_MEIZU_M2468=y`，源码 `drivers/gpu/drm/panel/panel-meizu-m2468.c`，440 行，默认 `M2468_MODE_FAKE`，只 `devm_drm_panel_add()`，且所有 `regulator_enable` 都有 NULL 保护）；
2. DTS 面板节点 `compatible` 改为 `meizu,m2468-panel`。

PE 结构正常（`.text` 0x00e2d000 + `.data`，与 v39 同构，仅大 4KB），FDT 头合法（magic `d00dfeed`，totalsize 0x20dba = 文件长 134,586）。**没有任何因体积导致的加载/布局异常**——14.73MB 能跑，14.87MB 没理由因为大 135KB 而废。真凶只能是这两处**内容**改动。

## 5. 顺手挖到的更关键线索：ESP 里的 dtb 很可能根本没被用到

- `esp_p2.img` 的 `dtb`（134,586 / f8add8c5）反编译后，`panel@0` 仍是 **`status = "disabled"`**，只把 `compatible` 改成了 `meizu,m2468-panel`。v39 的 dtb 也只有这一行不同。
- panel@0 `status=disabled` → of_graph 不收该节点 → `dsi_bind()` 的 `devm_drm_of_get_bridge()` 返回 -ENODEV → `msm_drm_bind()` 不执行。也就是说**按 ESP 里的 dtb，新驱动压根不会 probe**。
- 而 Mu 的 `FdtBlob/sm8550-meizu-21note.dtb`（12:20，134,582 / 8f81b0df）里，`panel@0` 是 `compatible="meizu,m2468-panel"` + **`status="okay"`**。
- Mu 的 `UfsWakeDxe.c` 注释写明 mkbootimg 布局 `kernel field = Mu, ramdisk = initramfs, dtb field = DTB`，且 `★待刷_v35_GPUCC.img` 内部确实嵌着 v35 ESP 那份 dtb 的副本（md5 3ab8d7c5）。→ **真正送进内核的 DTB 来自 Mu（boot_b）**，ESP 根目录那个 `dtb` 文件大概率是摆设。
- 时间线自洽：12:10 刷 panel2 时 boot_b 里的 Mu 还是旧的（panel 节点 disabled/旧 compatible），驱动不 bind，所以 12:19 的 `com16_out.txt` 还能读到 shell（它读到的正是 `compatible=boe,meizu20-amoled-fhd`、`status=disabled` —— 这份值只能来自旧 Mu 的 dtb）；而 **12:20 新 Mu（status=okay）才是真正让驱动 bind、进而把设备打死的那一步**。

## 6. 结论（按置信度）

1. **【确定】** `10,977,792` = `/home/shrp/esp_v35.img`（#37，2,790 行砍配置），是退化版；被验证可用的 v35 = `esp-v35-gpucc.img` 的 14,733,824（#54，4,698 行）。此前"两个事实冲突"是**比错了文件**，不是内核玄学。
2. **【确定】** panel2 内核 = 当前树 #60 的逐字节产物，与可用 v35 仅差 1 个 CONFIG 项 + 1 个 compatible 字符串。**体积差异不是失败原因**（13.5 万字节，PE/FDT 均结构合法）。
3. **【高置信】** panel2 的 ESP 本身很可能是好的（驱动在 ESP 自带 dtb 下根本不 probe）。失联更可能来自 **Mu 侧的 dtb / Mu 重编**：`status="okay"` 让驱动真 bind（prepare/reset GPIO/regulator/DSI attach 全程首次真跑），或 Mu FV 只剩 1432 字节余量导致打包静默失败（排查实录"坑 5"）。
4. **【待验证 1 步】** 只刷 `★待刷_panel2.img`（boot_b 保持旧 Mu）应能正常启动并拿到 COM16 —— 这一步就能把"内核/ESP 有问题"彻底排除。

## 7. 建议的下一步（不改内核）

- 实验 A（隔离变量）：旧 Mu + panel2 ESP → 预期能起、有 COM16、`panel@0` 仍 disabled。若成立，panel2 洗清。
- 实验 B：新 Mu（status=okay）+ **v39/v35 那个无驱动的内核**？不行 —— 无驱动时 okay 会让 dsi_bind 的 bridge 查找失败，仍无 card0。正确顺序是 A 之后再单独上 Mu_panel。
- 建议给 Mu 的 FdtBlob 加一道守卫：编完 Mu 后 `md5sum FdtBlob/*.dtb` 并与 `lmp73/.../sm8550-meizu-21note73.dtb` 对齐，同时检查 FV 剩余空间；FV 余量 < 4KB 时直接判失败。
- 驱动侧：在 `m2468_probe()` 首行加 `dev_info` 前先 `DRM_INFO("probe entered")`，并把 `prepare()` 的 regulator/GPIO 步骤逐条打点，方便下次失联时用"最后一条日志"定位——当前代码在 bind 失败时是静默的。
