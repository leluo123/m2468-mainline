## 这一夜推翻的三个旧结论

### ① 「改了 ESP 的 dtb」—— 从来没生效

```
错误做法:  改 ESP（rawdump/sda22）里的 dtb 文件
真实情况:  ESP 里的 dtb 从不被加载
真 DT 在:  Mu-Silicium/Platforms/Meizu/m2468Pkg/FdtBlob/sm8550-meizu-21note.dtb
           → 编译成 FVMAIN → 烧进 boot_b
证据:      BOOTAA64.EFI 里有 "Using DTB from configuration table"
           BOOTAA64.EFI 内 FDT magic 只有 1 次（代码常量）
           设备活 DT 的 md5 与 FdtBlob 不一致（改之前）
```

**P1/P2/P3 三个实验（删 dmas / ldo9 always-on / 去 spi-cpha）全部白做。**

**当时判断依据不足：DT 没生效，条件完全不同。这条结论不成立（未复现验证）。**

### ③ 「CS 极性 ACTIVE_HIGH 是错的」—— 无法证实

**改成 ACTIVE_LOW 后系统起不来，但那次的真因是 ESP 被破坏（见下）。**

## 真正走到最后的证据链

### 阶段 1：让 DT 真正生效（R1/R2/R4）

```
R1: spi-gpio 替代 GENI SE
    实测: spi@a90000 = disabled, spi-gpio = okay, spi0.0 注册成功
    结果: rx_buf: 00 00 00（不再是 -110 超时）★ 里程碑

R2: ldo12 加 regulator-always-on
    实测: vreg_l12b_1p8 从 disabled → enabled，1.8V
    结果: rx_buf: 00 00 00（vddio 不是根因）

R4: spi-gpio 的 pinctrl-0 加上 ts-irq(0x86) + ts-reset(0x87)
    原因: touchscreen@0 的 pinctrl 属于 goodix 驱动，
          probe 失败后 devres 释放 → pinctrl 未应用
          → gpio24(RST) 保持 XBL 的 mux=4，驱动控制不到物理引脚
    实测: gpio24 从 mux=4 → func0 8mA pull up  ✅
         所有 SPI 引脚 func0 正确
    结果: rx_buf: 00 00 00（RST 能控了，但 IC 还是不响应）
```

### 阶段 2：裸 bitbang 绕过一切框架

**脚本**：`/tmp/bb4.py`（串口传入，base64 分段）

**关键：先修正了自己脚本的三个 bug**（第一版读到的全是假数据）

```
pinctrl-msm 真实布局（drivers/pinctrl/qcom/pinctrl-sm8550.c:14,34-45）:
  REG_SIZE = 0x1000
  ctl_reg  = 0x1000 * id            GPIO_CFG
  io_reg   = 0x04 + 0x1000 * id     GPIO_IN_OUT   ← 不是 0x10！
  mux_bit  = 2   → bit[4:2]                        ← 不是 [2:0]！
  pull_bit = 0   → bit[1:0]                        ← 不是 [8:6]！
  drv_bit  = 6   → bit[8:6]                        ← 不是 [5:3]！
  oe_bit   = 9
  in_bit   = 0   (读值在 bit0)
  out_bit  = 1
```

**修正后的实测：**

```
gpio24 RST   : raw=0x02c3  mux=0 pull=3 drv=3 oe=1  IN=0
gpio25 IRQ   : raw=0x00c3  mux=0 pull=3 drv=3 oe=0  IN=1
gpio44 MOSI  : raw=0x0280  mux=0 pull=0 drv=2 oe=1  IN=0
gpio45 MISO  : raw=0x0080  mux=0 pull=0 drv=2 oe=0  IN=0
gpio46 SCK   : raw=0x0280  mux=0 pull=0 drv=2 oe=1  IN=0
gpio47 CS    : raw=0x0280  mux=0 pull=0 drv=2 oe=1  IN=1
```

### 阶段 3：MISO 上拉测试（决定性）

```
把 gpio45 配成 mux=0, pull=up(3), drv=0, oe=0
  → CFG = 0x0003  （pull=3 确认生效）
  → 但 IN = 0     ★★★
而 gpio25 配同样的 pull=up
  → IN = 1        （上拉功能正常）
```

**同一颗 TLMM、同样的上拉配置，gpio25 读 1，gpio45 读 0。**
**⇒ gpio45 这条线被外部持续拉低。**

## 结论：硬件故障

**三个可能：**

1. **触摸 IC 主动拉低 MISO** —— 处于某种异常/锁定状态（需要完全掉电才能解除）
2. **MISO 走线短路到地** —— 虚焊、进水、物理损伤
3. **IC 损坏**

**唯一还没做的验证：彻底断电（拔电池）让 IC 完全掉电重启。**

## 这一夜的额外收获（和触摸无关，但很重要）

### ⚠️ ESP 会被破坏

**故障现象**：刷 boot_b 成功、但系统完全起不来（黑屏无端口、无 COM16）

**真因**：ESP（rawdump/sda22，128MB）里的 initramfs 或 BOOTAA64.EFI 被破坏

**修复**：重刷 `E34_switchroot_esp128.img`

**表现对比**：
```
ESP 正常 → 串口 38 秒出现
ESP 损坏 → 等 10 分钟也无反应（但 fastboot 仍然正常）
```

**这个坑遇到过 2 次，每次都是「同一个镜像昨天能起今天不能起」才发现的。**

### ⚠️ panel 坏状态

**表现**：黑屏无端口，和 ESP 损坏一样

**区分方法**：先重刷 ESP，如果还不行，才是 panel 坏态

**修复**：刷原厂三件套 → 进 recovery（原厂驱动复位 panel）→ 回 fb

### ⚠️ 首启向导会吞掉串口命令

**表现**：串口发命令，输出变成 `Create root password: ****`

**处理**：
1. 逐字符慢速（150ms/字符）输入密码两次
2. Ctrl+C 跳过用户创建
3. 之后 devfs 正常

**这个向导每次刷 userdata 后都会跑（因为 `armbian_first_run` 标志没持久化）。**

## 触摸如果再想推进，只有两条路

**A. 物理断电**
拔电池（或等电量耗尽），让触摸 IC 彻底掉电。这是唯一能解除「异常锁定状态」的软件做不到的事。

**B. 硬件检查**
- 量 gpio45 (MISO) 对地电阻 —— 短路会接近 0Ω
- 检查 FPC 排线是否松动/氧化
- 用示波器看 SCK/MOSI 是否有波形（我的 bitbang 脚本确实在翻转，但没示波器无法确认电平时序）

**软件侧已经没有可做的了。**
